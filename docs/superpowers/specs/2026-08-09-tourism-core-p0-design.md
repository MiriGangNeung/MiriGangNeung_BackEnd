# 관광공사 핵심 장소 API P0 설계

> 상태: 승인됨
> 작성일: 2026-08-09

## 목표

프론트엔드가 사용할 장소 검색·목록·상세 데이터를 한국관광공사 TourAPI `KorService2`에서 안정적으로 공급한다. 기존 `PlaceService`와 REST 컨트롤러의 외부 계약은 유지하면서, 관광공사 응답을 내부 장소 모델로 정규화하고 실패·캐시·이미지 처리를 보완한다.

## 현재 문제

- `KoreanTourApiClient`가 요청 조립, JSON/XML 파싱, 도메인 매핑을 한 클래스에서 모두 처리한다.
- 현재 `related()`가 관련 관광 API가 아닌 `detailInfo2`를 호출한다.
- 관광공사 오류 응답의 `resultCode`를 확인하지 않아 오류가 빈 결과로 숨겨질 수 있다.
- `detailImage2`를 사용하지 않아 장소 이미지 목록이 비어 있다.
- 내부 `Place.sourceUpdatedAt`이 원천 데이터의 갱신 시각과 연결되지 않는다.
- 검색 시 전달된 카테고리가 관광공사 요청과 내부 조회에 일관되게 반영되지 않는다.
- `RedisCache` 유틸리티는 있으나 장소 조회 흐름에 연결되어 있지 않다.

## 범위

### P0에 포함

다음 `KorService2` 오퍼레이션을 사용한다.

- `areaBasedList2`: 강릉 지역별 장소 목록
- `searchKeyword2`: 키워드 검색
- `detailCommon2`: 장소 기본 상세·좌표·대표 이미지·수정 시각
- `detailIntro2`: 장소 유형별 운영 정보의 확장 지점
- `detailImage2`: 장소별 추가 이미지 목록 및 저작권 구분 코드

P0의 외부 응답에서 현재 도메인이 표현할 수 있는 값은 우선 `Place`와 `PlaceImage`에 매핑한다. 운영 정보 중 현재 모델에 없는 값은 임의의 필드로 흩뜨리지 않고 별도 확장 DTO를 통해 다음 단계에서 노출할 수 있도록 파싱 경계를 둔다.

### P0에서 제외

- 관련 관광지 `TarRlteTarService1`
- 관광지 중심지 `LocgoHubTarService1`
- 혼잡도 예측 `TatsCnctrRateService`
- 방문자 수 DataLab API
- 별도 사진 갤러리 API
- AI 합성 워커·실제 AI provider
- 카카오 경로 polyline 및 코스 자동화 고도화

위 API는 핵심 장소 데이터 계약이 고정된 뒤 P1에서 각각 별도 어댑터와 테스트를 추가한다. `related()`는 P0에서 잘못된 `detailInfo2` 호출을 외부 관련 관광 데이터처럼 사용하지 않도록 동작을 명확히 정리한다.

## 설계

### 1. 어댑터와 정규화 계층

기존 `TourApiClient`를 애플리케이션 포트로 유지한다. `KoreanTourApiClient`는 관광공사 요청·응답 어댑터 역할만 담당하고, 응답을 공통 정규화 DTO로 변환하는 책임을 분리한다.

정규화 결과에는 다음을 포함한다.

- 관광공사 `contentid`, 이름, 주소, 좌표, 관광 유형, 설명
- 대표 이미지와 추가 이미지
- 원천 수정 시각
- 이미지 저작권 구분 코드
- 원천 서비스명

요청 공통 파라미터는 `serviceKey`, `MobileOS`, `MobileApp`, `_type`, 페이지 파라미터를 한 곳에서 조립한다. 검색·목록은 강릉의 `lDongRegnCd=51`, `lDongSignguCd=150`을 사용하고, 관광 유형은 내부 카테고리와 `contentTypeId`를 명시적으로 변환한다.

### 2. 오류와 빈 응답

- HTTP 오류, 네트워크 오류, 타임아웃은 외부 연동 예외로 구분한다.
- HTTP 200이어도 `header.resultCode`가 성공 코드가 아니면 오류로 처리한다.
- 성공했지만 `items`가 없는 경우만 정상적인 빈 결과로 반환한다.
- 외부 오류 메시지와 내부 로그에는 원천 서비스·오퍼레이션·요청 식별 정보를 남기되 API 키는 절대 기록하지 않는다.
- 장소 검색의 일시적 외부 실패는 기존 DB 결과를 활용할 수 있는 경로를 유지하고, 상세 조회처럼 대체 데이터가 없는 경우에는 기존 전역 예외 규칙에 맞는 오류를 반환한다.

### 3. 저장과 이미지

`PlaceService`가 정규화된 장소를 upsert할 때 원천 수정 시각과 대표 이미지를 갱신한다. 추가 이미지는 `PlaceImage`의 정렬 순서와 저작권 구분을 보존할 수 있도록 확장한다. 기존 데이터와 중복되지 않게 `tourContentId`를 기준으로 저장한다.

이미지 원본 URL은 백엔드가 그대로 프론트에 전달하되, 관광공사 이용약관·저작권 표시가 필요한 값은 응답 모델에 남긴다. 이미지가 없는 장소도 장소 본문 자체는 정상 반환한다.

### 4. 캐시

장소 목록·키워드·상세·이미지 조회를 서로 다른 키 공간으로 캐시한다. 키에는 요청의 의미 있는 파라미터와 페이지를 포함하고 API 키는 포함하지 않는다. 캐시 TTL은 목록·검색과 상세를 분리하고, 캐시 장애가 장소 API 전체 장애로 전파되지 않도록 우회한다.

### 5. 테스트 전략

- 관광공사 JSON/XML 성공 응답 정규화 단위 테스트
- `resultCode` 실패, HTTP 실패, 잘못된 응답, 빈 `items` 테스트
- 검색·목록·상세·이미지 요청의 endpoint와 핵심 query parameter 테스트
- 카테고리와 `contentTypeId` 매핑 테스트
- `PlaceService` upsert 및 이미지 중복 방지 테스트
- 캐시 적중·실패 우회 테스트

외부 관광공사 서버에 의존하는 테스트는 만들지 않는다. 테스트는 고정된 응답 fixture와 HTTP 경계 mock을 사용한다.

## 구현 순서

1. 응답 정규화 모델과 성공·실패 파서
2. `KorService2` 목록·검색·상세·이미지 요청 연결
3. 카테고리·원천 시각·이미지 저장을 `PlaceService`에 연결
4. 캐시와 외부 오류 fallback
5. 기존 장소·코스 흐름 회귀 테스트 및 전체 검증

각 단계는 실패 테스트를 먼저 추가하고 통과시킨 뒤 다음 단계로 넘어간다.

## 완료 조건

- 백엔드 장소 목록·검색·상세 API가 실제 관광공사 계약에 맞는 요청을 생성한다.
- 관광공사 성공 응답의 장소·이미지·수정 시각이 내부 모델에 저장된다.
- 외부 오류가 빈 성공 응답으로 위장되지 않는다.
- 캐시 장애 시 원래 장소 조회 경로가 동작한다.
- P0 관련 테스트와 기존 테스트가 모두 통과한다.
- P1 API를 위한 경계와 미구현 범위가 문서로 명확하다.
